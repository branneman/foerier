# S11 — Reopen

*Delivers story 11b. Advances story 32 (the reopen clause). Closes two entries
in [`technical-debt.md`](../technical-debt.md).*

The tent marked `lost` in September turns up in November, and the record can be
corrected without lying about it. That is story 11b's own sentence, and until
this slice it is **half true**: a Trip whose close owed the Depot nothing
reopens exactly as drawn, and a Trip that burned two gas canisters cannot be
reopened at all. The route is withheld today by `reopenBlocked`
(`shared/src/gestures.ts`), because `close → reopen → close` subtracted the
same units twice — owned 6 → 4 → reopen → **2**, four taps, no crash, nothing
on screen.

S11's job is therefore two jobs, and the second is the one
[`design/README.md` §5j](../design/README.md) names as not optional: make the
re-close subtract nothing twice, **and hand the route back**.

Its design was not ruled at a board round. Every decision it takes is recorded
in `design/README.md` **§5k** in the same commit, for §5g's own reason — a code
decision no board reaches is invisible to the next design round.

## 1. The defect, stated once

`gear.owned_count_set` is **absolute, never a delta**
([sync §4.3](../sync-protocol.md)) — which is exactly what makes two Devices
closing the same Trip safe, and exactly what makes a *second* close of the
*same* Trip wrong. `closeTrip` computes `owned − consumed` against the fold it
is handed. A reopened Trip folds to `unpack` indistinguishably from a Trip that
was never closed, so `closeTrip`'s own `isClosed` guard cannot see it, and the
second close recomputes from the already-reduced count.

Two mechanisms were considered and refused before this slice, and both refusals
stand:

- **A cross-aggregate stamp comparison** (ruling R28, the shape `unaccountedOf`
  already uses) reads as a **false negative** — silently skipping a reduction —
  exactly when a Quartermaster corrects the owned count between declaring the
  consumption and closing. A comparison against the Trip's *phase* stamp fails
  harder: invariant 16 lets an outcome be recorded before the move into
  `unpack`, so on an ordinary **first** close every outcome stamp can precede
  the phase stamp and the reduction would be skipped outright.
- **Restoring the owned count on reopen** is story 11's own refusal: the
  restoration is *offered* and waits for a human, *"it never silently rewrites
  a count I may have already corrected by hand"*. Ruling G1 draws the same
  answer as a fact line — `OWNED COUNTS LOWERED AT CLOSE STAY LOWERED`.

What is left is the mechanism both technical-debt entries and §5j name: a
**per-Trip-per-Gear "already posted" register**. It is one op type, and §4
argues its legitimacy against §8.3's own instruction to check the domain rather
than invent a row.

## 2. The register and the arithmetic

### 2.1 The op

```
trip.consumption_posted   { gear_id: <uuid>, units: <int ≥ 0> }
```

Two segments, `snake_case`, past tense ([sync §5.1](../sync-protocol.md)).
`aggregate` is `trip`, `aggregate_id` the Trip. It folds to

```
trips.<trip_id>.postings.<gear_id> : Register<number>
```

— a new row in [sync §3.7](../sync-protocol.md)'s register map, on the **root**
entity path beside `participants`. Per-gear registers rather than one register
holding a map, for §3.4's standing reason: two Devices posting different Gear
address different registers and both survive; two posting the *same* Gear is one
register resolving by plain LWW, and both compute the identical value from the
identical fold, so LWW picks between two equal numbers.

**`units` is absolute, never a delta** — `gear.owned_count_set`'s own contract,
restated one register over and for the same reason. It is the running total this
Trip has posted against that Gear's owned count, so re-emitting the same value
is idempotent and a Device that folds the op twice learns nothing new.

**It folds unconditionally.** The reducer writes the register whatever the
Trip's phase, whatever the Gear's Kind, and whether or not `state.gear[gear_id]`
has arrived — `bringCountOf`'s and `consumedCountOf`'s rule again, and for the
identical reason: the Kind lives on the Gear aggregate, which has no ordering
against the Trip's, so gating in the reducer would make the fold depend on
whether `gear.kind_set` happened to arrive first. Every gate is a **reader**
gate, in `postedOf` and its callers.

**An absent register reads `0`**, and only `postedOf` (`unpack.ts`) says so.
This is the same shape as `ownerOf`'s `SHARED`, `phaseOf`'s `draft` and
`statusOf`'s `not_packed`, with the same symptom when a call site re-derives it:
a Trip that owes nothing being reduced again. Absent and an explicit `0` stay
different facts about the log — absent means no close ever posted this Gear, `0`
means a restoration took it back to nothing — and every reader treats them
alike.

### 2.2 One number, three places

```
owed(trip, gear)   = consumedReductions(trip, state).get(gear) ?? 0   // unchanged
posted(trip, gear) = postedOf(trip, gear)
delta              = owed − posted
```

| Sign | Who acts | What happens |
| --- | --- | --- |
| `delta > 0` | **the close** | `gear.owned_count_set(max(0, owned − delta))`, then `trip.consumption_posted(gear, owed)` |
| `delta = 0` | nobody | no write at all — this is what makes a re-close free |
| `delta < 0` | **the offer** (§3), never the close | the close skips it silently; a human is asked at the moment the change is made |

`consumedReductions` is untouched and stays the one question — it already gates
a `consumed` outcome to a Counted **depot** Entry, so a container, a Single, a
trip-only Entry and an unsynced Gear each contribute nothing, and it is the
identical read `ReopenConfirm` asks for its disclosure line. Re-deriving `owed`
anywhere is the drift `gestures.ts`'s own header argues against.

### 2.3 `closeTrip`, changed only inside its loop

Both existing early returns stay — `isClosed` (R27 Layer B) and
`unpackTotals(...).open > 0` (R36). The loop gains the posting:

```ts
for (const [gearId, owed] of consumedReductions(trip, state)) {
  const delta = owed - postedOf(trip, gearId)
  if (delta <= 0) continue                       // §2.2's middle and bottom rows
  const owned = ownedCountOf(state.gear[gearId]) ?? 0
  ops.push(gearOwnedCountSet(gearId, Math.max(0, owned - delta)))
  ops.push(tripConsumptionPosted(trip.id, gearId, owed))
}
ops.push(tripPhaseMoved(trip.id, 'closed'))
```

**Op order inside the batch is a decision, not an accident.** `emit` appends one
op at a time (`store.ts`), so a gesture is not atomic and a Device can die
between any two. The reduction goes **before** its posting for the same shape of
reason `trip.phase_moved` goes last: a posting recorded without its reduction
would make every later close skip a reduction that never landed — a silent
under-count, R28's own failure mode arriving by a different door — whereas the
reverse leaves the pre-existing behaviour exactly as it is today.

**This does not close the crash-mid-batch debt, and deliberately does not
pretend to.** A Device that dies after the reduction lands durably and before
the posting does still re-reduces on retry. That is a separate entry in
`technical-debt.md`, it is unchanged by this slice, and closing it would need
the two ops to land atomically — a store-level change with no relation to
reopening. The entry is rewritten to say that the register now exists and that
what is missing is atomicity, not a fact.

`Math.max(0, …)` stays: a Trip cannot reduce a Gear's owned count below nothing.

## 3. The offer

Story 11: *"Changing away from `consumed` **offers** to put the Owned-count
back and waits for me to confirm — it never silently rewrites a count I may have
already corrected by hand."* Domain §6 says the same about a reopened Trip.

**The trigger is one predicate, not two.** The offer fires whenever a change
makes `owed < posted` for a Gear — which is the negative `delta` the close
refuses to write, surfaced to a human. That covers both cases with one rule:

- the outcome moves off `consumed` (to `back`, to `lost`, or cleared) — `owed`
  falls to `0`;
- the Consumed-count is lowered from `×4` to `×2` — `owed` falls to `2`.

Deriving the second from its own rule later is how two numbers drift; the
literal reading of the story ("only on leaving `consumed`") would leave a
lowered count with units deducted and nothing offering them back.

**It is a `Confirm`, raised by `OutcomeSheet` after the change is emitted.**
Ruling G15 already finishes the derivation — *the confirm is owed where the act
cannot be seen on the screen that made it* — and the Depot's owned count is not
on F5. The change itself is never held hostage by the offer: the outcome op is
emitted first and stands whether or not the offer is taken, which is what makes
`Leave it` truthful.

```
Put ×4 back on Gas canister 450?
Alps 2026 lowered the owned count when it closed. It goes back to what
it was before that close.
                              GAS CANISTER 450 ×2 → ×6
                     [ Put it back ]   [ Leave it ]
```

Confirming emits, in this order:

```
gear.owned_count_set(gear, owned + (posted − owed))
trip.consumption_posted(trip, gear, owed)
```

— the absolute target computed from the count **now**, so a count corrected by
hand since the close is raised by what this Trip took and not reset to a number
nobody recorded. Posting-after-restoring, for §2.3's reason mirrored.

**Declining is a decision that stands.** The posting is not lowered, so the
units stay deducted — G1's `COUNTS LOWERED AT CLOSE STAY LOWERED` as the
default — and a later re-raise of the Consumed-count to `×4` posts the
difference only, never the whole amount again. The offer is not re-raised at
the close: the close applies positive deltas and never restores, which is
§2.2's table with no exception.

`restoreConsumption(trip, gearId, owed, state)` is the third function in
`gestures.ts`, for the reason the first two are there: it composes two payload
builders with a read of the fold, and spelling it once means a second caller
cannot emit half of it.

**It cannot fire on a Trip that was never closed**, and this falls out of the
arithmetic rather than needing a phase check: `posted` is `0` on such a Trip, so
`owed < posted` is unreachable. The offer is therefore self-limiting to exactly
the reopened Trips story 11 describes.

**It does not fire on a closed Trip either**, because on a closed Trip no such change
can be made: G6 makes F5 a record and withholds every write, and `OutcomeSheet`
already withholds the Consumed stepper on `isClosed`. The offer inherits that
gate rather than restating it.

## 4. Why one new op type, against §8.4

[§8.4](../architecture-design.md#84-story-11-is-two-slices) argues the 11a/11b
seam on one decisive sentence: **"11b introduces no new op types at all."** This
slice falsifies it, by exactly one, and the honest thing is to say so rather
than edit the claim away.

The seam is still in the right place, and the argument survives with one word
changed. 11a carried two op types, two cross-aggregate gestures, the
claim-release rule and the whole close gate; 11b carries one op type that writes
one register nothing else reads. It cannot break 11a's merge behaviour, because
it addresses a register 11a never wrote. What §8.4 got wrong is not the seam but
the *count*, and it got it wrong for a reason worth keeping: at planning time the
double-subtraction had not been found, because nothing in the plan draws the
`close → reopen → close` path.

[§8.3](../architecture-design.md#83-the-slices) instructs that a slice needing
an op outside the catalogue *"is a signal to check the domain, not to invent a
row"*. Checked, and the domain answers:

> **domain §6:** the owned-count falls by the consumed-count … **It applies
> once, at the close**; a later change to the outcome on a reopened trip
> **offers** the correction for confirmation rather than silently re-applying
> it, because the depot may have moved on since.

*Applies once* is a domain assertion with nowhere in the model to be recorded.
The Trip records what it consumed; the Depot records what is owned; nothing
records that the transfer happened. That is a genuine gap in the model rather
than a convenience for the code, and it is filled by naming the thing the
domain already talks about: a **posting**, the moment a Trip's consumption is
applied to the Depot. The glossary gains the term, domain §9 gains the
operation, and the invariant it supports is stated where invariant 8 already
lives.

Everything else about story 11b remains what §8.4 says it is: UI, selector,
guard and convergence-test work over ops that already exist.

## 5. Handing the route back

### 5.1 `reopenBlocked` is deleted

Not narrowed — deleted, along with its export from `shared/src/index.ts` and its
three call sites. The predicate exists to answer *would a re-close
double-reduce*, and after §2 the answer is no on every Trip.

**Three code-authored strings retire with it**, exactly as §5j promised:

| Where | Retires | Returns |
| --- | --- | --- |
| `Trips.tsx`, the closed ledger row's meta | `NO REOPEN — COUNTS LOWERED AT CLOSE` | `REOPEN` on every closed row |
| `PhaseSheet.tsx` | the one-row `CLOSED` sheet, and `CLOSED — COUNTS LOWERED AT CLOSE. NO DATE OR COUNT EVER MOVES A PHASE.` | all four rows out of `closed`, and `ANY ROW TAPPABLE, BACKWARDS INCLUDED. …` |
| `Unpack.tsx`, `CLOSE_HINT_CLOSED_NO_REOPEN` | `CLOSED · OUTCOMES ARE HISTORY. NO REOPEN — COUNTS LOWERED AT CLOSE.` | G6's `CLOSED · OUTCOMES ARE HISTORY. REOPEN TO CHANGE ONE.` |

**G1's disclosure line becomes reachable for the first time.** It is not
changed: it is the same conditional mono block, on the same predicate, stating
the same fact — and it is now true of Trips a Quartermaster can actually open
the sheet on. The comment marking it unreachable is removed; the caveat it
carries about `×6` being a reconstruction stays, and gains a sibling (§5.2).

**G7's cost is repaid.** *"Reopen is the route"* to correcting a closed Trip's
outcomes stranded when the gate landed; the route exists again, and the sheet
no longer has to avoid pretending it does.

### 5.2 `reopenTrip` back-fills a pre-S11 close

A closed Trip in a real household today was closed by a build with no posting
op. Its `postings` map is empty and its `owed` is `×4`, which is
indistinguishable from *nothing was ever posted* — so a naive re-close would
reduce a second time and S11 would have handed back a broken route.

`reopenTrip` therefore records what that close already did, before moving the
phase:

```ts
export function reopenTrip(trip, to, state): readonly OpSpec[] {
  if (!isClosed(trip)) return []
  const ops: OpSpec[] = []
  for (const [gearId, owed] of consumedReductions(trip, state)) {
    if (trip.postings?.[gearId] !== undefined) continue   // already recorded
    ops.push(tripConsumptionPosted(trip.id, gearId, owed))
  }
  ops.push(tripPhaseMoved(trip.id, to))
  return ops
}
```

**It is legitimate, and the reason is G6.** F5 on a closed Trip is a *record*:
every write is withheld, so a closed Trip's outcomes are frozen and
`consumedReductions` computed now is what that close applied. This is a
reconstruction from a fact that cannot have moved, not a guess — the same
standing the `×6` in G1's line already has, and the same caveat: a peer on
another build that *did* change an outcome on a closed Trip makes the
reconstruction state a number that was never posted. Recorded, not guarded.

The `undefined` check reads the register's own presence rather than
`postedOf`'s `0`, and this is the one place the two differ on purpose: a
posting explicitly restored to `0` (§3) is a Gear whose close *was* recorded and
whose units have been handed back, so it must not be back-filled. It is also
deliberately per Gear rather than *is the whole map empty* — a Trip closed by
this build, then given a `consumed` outcome on a second Gear by a peer that
ignores G6, has a partial map, and the narrower check back-fills only what is
missing.

The gesture keeps its `to` from the caller — the closed ledger row targets
`unpack`, `PhaseSheet` offers all four rows — and its docblock's *"this gesture
decides whether, never where"* becomes simply *"where is the caller's"*, since
after §2 there is no whether left to decide.

### 5.3 What is still not reachable, stated rather than implied

A peer on a **pre-gate** build — S10-era, before `reopenBlocked` shipped — can
still reopen a closed Trip with a bare `trip.phase_moved` and no posting. Such a
Trip syncs here as an ordinary `unpack` Trip whose postings are empty, and this
build's close reduces from the already-reduced count.

This is narrower than what §5j records today in two ways worth naming: it needs
a build **two** releases old rather than one, and it needs that Device to be the
one that performs the reopen — a reopen through any current build back-fills and
the hazard never arises. It cannot be closed from this side at all, because the
only evidence is an op that build never wrote. Recorded in `technical-debt.md`
as a shrinking cross-version residue rather than as outstanding work.

## 6. `ReopenConfirm`'s last mono block

The sheet has carried a note since S6 that one drawn block is unbuilt:
`1 ENTRY STILL OPEN — HEADLAMP, K · ▲ LOST`, held for S11.

**The board's two halves disagree, and the standing is the half that survives.**
A properly closed Trip has zero open outcomes — invariant 18 is what the close
is gated on — and a `lost` Entry is *resolved*, not open. The drawn `▲ LOST`
cannot be produced by an open count. What the block is for is legible from
story 11: the reason a Quartermaster reopens is the tent that turned up, so the
block states **what about this Trip is still unsettled**.

```
1 STILL UNACCOUNTED — HEADLAMP, K · ▲ LOST
```

- `standingLostOf(trip, state)` is a new function in `unpack.ts`: the Trip's
  Entries and Pieces whose `lost` outcome **still stands**, through
  `outcomeStands`, which is the one definition of that and is never re-derived.
- It is **not** `unaccountedOf`. That selector is keyed by Gear across the
  household and names the *latest* Trip holding a live `lost` — so on a Gear
  lost twice it would name someone else's Trip in this Trip's own sheet.
- The count is units, matching every other count on the sheet; the names follow
  the fact-line grammar already ruled (`·` divides segments, the comma divides
  values inside one), and a Person renders through `personNameOrUnnamed`.
- **Absent at zero** (G3), which is the ordinary case — a Trip closed with
  everything `back` shows no block, exactly as it shows no reduction line.

The three conditional blocks now stack in one order inside the sheet's single
`children` slot: the unaccounted block (what is unsettled about this Trip),
G1's reduction lines (what the close did), then the facts-only over-claim block
(what reopening would collide with) — this Trip's own history first, the world
outside it last.

## 7. What is already built and becomes a test obligation

Two of S11's listed deliverables need no implementation, and saying so is part
of the design:

- **The over-claim warning at the reopen moment, which never refuses the
  reopen.** `ReopenConfirm` already renders `overClaimsIfActive` through
  `OverClaimGroups` with no `settle` (ruling I, facts-only), gated on
  `isActivePhase(to)` so a reopen into `draft` states nothing. Story 32's *"it
  never refuses to reopen"* is structural: the block is a paragraph, not a gate.
- **"The retained packing arrangement comes back into effect."** §8.4 already
  argues this is not implementation work: nothing is destroyed to close, and
  active-ness derives from `phase`, so the arrangement returns for free. It is a
  convergence-tier assertion and lands as one.

## 8. Tests

**Tier 0** — full-repo `tsc`, ESLint, Prettier, as every slice.

**Tier 1 (`shared/`)**

- The reducer folds `trip.consumption_posted` unconditionally: unknown Gear,
  every phase, a Kind that is not Counted. Absent reads `0` through `postedOf`
  alone.
- `closeTrip`: a first close posts `owed`; a **second** call against a fold that
  already reflects the first emits **no** `gear.owned_count_set` — the four-tap
  path, asserted end to end as `close → reopen → close` over one fold.
- `closeTrip` against the *same, unchanged* state twice is byte-identical
  (S10's assertion, kept — the posting must not break it).
- A negative delta is never written by the close.
- A Trip listing one Gear on two Entries posts one op summing both.
- `reopenTrip` back-fills exactly the Gear with no posting recorded, skips one
  explicitly restored to `0`, and posts nothing on a Trip that owes nothing;
  the phase move is last.
- `restoreConsumption` computes its absolute target from the count **now**, so a
  hand correction between close and reopen is raised rather than overwritten.
- `standingLostOf` returns only standings that still stand, and returns them for
  Pieces as well as Entries.
- `reopenBlocked` is gone: its tests are deleted, not skipped.

**Tier 2 (convergence)** — the signature tier, and this slice's two obligations:

- **Two Devices close, reopen and re-close the same Trip and converge on one
  owned count**, in both interleavings. This is the property the whole slice
  exists for, and it is the reason `units` is absolute.
- **A reopened Trip's retained packing arrangement comes back into effect on
  every replica** — statuses, residences, journeys and outcomes, none of them
  written by the reopen.
- A posting and a hand `gear.owned_count_set` racing: the registers are on
  different aggregates and cannot make each other disappear.

**Tier 3 (`app/`)** — the restoration offer (raised, confirmed, declined, and
the outcome standing either way); `REOPEN` present on every closed ledger row;
`PhaseSheet` drawing four rows out of `closed` with its footnote restored;
F5's closed hint reading G6's form; `ReopenConfirm`'s three blocks and their
order.

**Backward compatibility** — `s11-reopen.ops.json` captured **in this commit**,
carrying `trip.consumption_posted` at the shape §5.4 freezes the moment it
ships. S4's fixture debt is the reason this sentence is here rather than
assumed.

## 10. What this slice does not do

- **It does not make the reduction atomic.** The crash-mid-batch window is
  untouched (§2.3).
- **It does not restore a count on reopen.** §5j refused it and story 11 is why;
  the offer in §3 is the whole of the restoration.
- **It does not add a corrections surface to a closed Trip.** G7 declined one
  and named reopen as the route; the route is back, and that is the answer.
- **It does not touch the slicing engine, any endpoint, any migration, or
  `state.ts`'s Entry and Piece paths.** One register, on the Trip root.

## 11. What changed during implementation

The things this spec states that are wrong or incomplete against what shipped. They
are recorded here rather than edited into the sections above, following
[`2026-08-29-the-gear-list.md` §11](2026-08-29-the-gear-list.md#11-what-changed-during-implementation)'s
precedent: **a dated spec is left as it was written**, and what changed lives in
its own section. The rulings this slice's code took that no board reached are a
different list and live in [`design/README.md` §5k](../design/README.md), which
is the shipped authority for them.

### 11.1 §3 names the wrong closed-Trip gate

§3's last paragraph says the offer cannot fire on a closed Trip because
*"`OutcomeSheet` already withholds the Consumed stepper on `isClosed`"*. The
conclusion is right and the reason is wrong. `showStepper` gates the Consumed
stepper alone; the **outcome chips stay live** if the sheet mounts, so a
`consumed → back` tap on a closed Trip would reach the trigger through the
outcome path that paragraph never considered. What actually holds is one
layer up: ruling G6 makes F5 on a closed Trip a *record*, so `Unpack.tsx`'s row
routing draws the outcome as text and sends the row body to gear detail — the
sheet is **never mounted** on a closed Trip at all. The offer inherits the gate
by never running, which is what §3 meant to claim. Both the code's docblock and
this section say so, because a future author narrowing G6 needs to know that
this trigger is one of the things leaning on it.

### 11.2 The trigger needed a `before !== after` guard §3 implies but does not state

§3 says the offer fires when a change *makes* `owed < posted`. The word is
load-bearing and the spec never turns it into a rule. Without a guard, the
predicate reduces to *the state now reads `owed < posted`*, which is a standing
condition rather than a change: declining the offer once leaves exactly that
state — G1's own default, counts stay lowered — and any later, unrelated outcome
change on the same Entry re-raises it. `back → lost` moves no units and has
nothing to offer, and it would have offered. The shipped predicate compares this
Entry's own contribution to `owedOf` before and after the change and returns
early when they are equal.

### 11.3 `standingLostOf`'s settle is household-wide; the first implementation narrowed it to the Trip

§6 says the block reads *"through `outcomeStands`, which is the one definition
of that and is never re-derived"*, and the first implementation re-derived it
anyway — a trip-local reconstruction of the same argument, gathering settles
from this Trip's own Entries alone. That is wrong in **story 11's own motivating
case**: a tent marked `lost` on Alps (closed) and brought `back` on Tessin is
settled, the Depot draws no `▲`, and a Trip-local settle would still have
printed `1 STILL UNACCOUNTED` on Alps's reopen sheet — the sheet contradicting
the Depot about the same Gear. Two settle routes are named identically by story
3, story 11 and `domain-model.md`, and none of the three scopes the second one.

The split that survived review is worth stating, because "not `unaccountedOf`"
turns out to mean two different things: **candidates** are trip-local (what
*this Trip* recorded, so the sheet never attributes a standing to another Trip's
name), while the **settle** is a household fact. Both `standingLostOf` and
`unaccountedOf` now share one `settledOutcomeStamps(state)` pass, so there is
one copy of *what counts as a settle* rather than two that agree today.

### 11.4 A convergence guard the plan never named

`convergence.test.ts` asserts that its own property generator emits **every op
type the reducer folds**. Adding `trip.consumption_posted` therefore turned the
tier red before a single property about it was written, and stayed red until an
arbitrary existed. Neither this spec's §8 nor the task plan mentions it. Worth
recording because **every future slice that adds an op type inherits it** — the
tier's redness is the intended behaviour, not an obstacle, and the fix is always
to generate the op rather than to relax the assertion.

### 11.5 `closeTrip`'s new batch broke three existing `app/` assertions

Three tests pinned `closeTrip`'s exact emitted op array, and the posting is a
second op inside the loop. Expected, and they were **updated to the three-op
order rather than loosened** to *contains these ops*: §2.3 argues that
reduction-before-posting-before-phase-move is a decision about what a partial
batch leaves behind, so the order is load-bearing and an assertion that stops
seeing it is an assertion that stops protecting it.

### 11.6 The posting records what the close **applied**, not what it owed

§2.2's table and §2.3's code block both write `trip.consumption_posted(gear,
owed)` beside a reduction floored at `Math.max(0, owned − delta)`. The
reduction is floored and the posting is not, and **over-claim is a supported
state** — S7 surfaces it and never blocks it — so the two diverge: owned ×1
with ×5 consumed closes to `0` and posts `5`. Reopen, tap the outcome to
`back`, `Put it back`, and `restoreConsumption`'s `owned + (posted −
owed)` hands back `0 + (5 − 0)` = **×5** on a Gear the household owns one
of — four ordinary taps, one Device, no crash, which is the exact shape of
defect this slice exists to remove.

This is a **code bug against §2.1**, not a change to it: the register is
defined there as *"the running total this Trip has posted against that Gear's
owned count"* — the applied amount, and `owed` is the declared one. What
shipped is `applied = min(delta, owned)`, with the reduction writing `owned −
applied` and the posting `posted + applied`, an absolute running total. The
close's own docblock carries the argument. Three consequences worth stating:

- A close the Depot can only partly satisfy posts the part it satisfied, and a
  later close against a restocked shelf applies the remainder and lands the
  running total on `owed` — reached in instalments, never exceeded.
- `restoreConsumption` still posts `owed`, which is exactly what stays applied
  once it has handed back `posted − owed`. The two arithmetics compose over any
  number of rounds.
- `applied === 0` writes **nothing** when this close is already on the record
  for that Gear (the re-close after a declined offer: `owned` is `0`, both ops
  would be needless writes) and posts the `0` when it is not. The second half
  is not symmetry for its own sake: absence is what §5.2's back-fill reads as
  *this close was never recorded*, so without it the back-fill would fabricate
  a posting of the whole `owed` for a close that applied nothing and re-open
  the same over-credit through a second door. §5.2's reconstruction is
  unchanged and keeps its own limit — a **pre-S11** close that was itself
  floored is back-filled at `owed`, because the pre-close owned count exists
  only in the log.

The same correction reaches `ReopenConfirm`'s G1 disclosure block, which built
its line from `consumedReductions` and so under-stated the arrow whenever a
Consumed-count had been lowered, and **vanished entirely** once a restoration
was declined and the Trip re-closed — on the one Trip where the line is most
true. It reads `postedOf` where the register is present and falls back to the
reconstruction where it is not, which is §5.2's own rule; the comment claiming
*"there is no register that would answer better"* was written before the
register existed and is deleted. Ruled in `design/README.md` §5k.
